# headroom — design for the scale you actually have (and the next one)

The first question is never "which database". It is: **what scale exists
now, and what scale are we actually designing for?** Every recommendation
that follows carries the load level at which it becomes necessary. A
50-user college project must not become Netflix — and a system about to
10× must not pretend a single box is fine forever.

## When NOT to use

- Documenting what exists → `blueprint`.
- A specific endpoint is slow → that's diagnosis (hotpath, planned phase
  4), not design.
- Implementing backend behavior → `backend`.

## Prerequisites

Numbers, or honest estimates. Ask for: current users/traffic, request
profile, data size, growth expectation, availability needs, budget
reality. Anything the user can't provide gets an explicitly-labeled
estimate with its arithmetic shown — never cargo-cult numbers ("millions
of requests") the user never claimed.

## The proportionality rule

Every recommendation states the trigger: the metric at which it becomes
necessary ("add a read replica when sustained DB CPU > 60% or reads > 5×
writes"). A recommendation without a trigger is a guess wearing a suit.

## Evaluation

Walk the dimensions in `references/dimensions.md` — read only the ones
the decision at hand actually touches; for a typical design review that's
6–10 of them, not all 22. For each: current state, what breaks first, and
which level's recommendation covers it.

## Output: three levels

**Now** — what's appropriate today. Boring, operable by the current team,
cheap to reverse. This is where most projects should stay.

**Next** — what becomes necessary as usage grows. Each item names its
trigger metric and the migration path from Now. This is the "leave
headroom" layer: choices today that keep Next cheap (e.g. keep SQL until
sharding is real; put a queue boundary where work is bursty).

**Scale** — the architecture for materially larger traffic. Sketches with
trade-offs, not runbooks. Explicitly marked "do not build today".

Each level: the decisions, why, what breaks without it, and rough cost
shape. The gaps **between** levels are the actual advice — they tell the
user what they're deliberately not doing yet.

## Honesty rules

- Back-of-envelope arithmetic is encouraged and shown: `200 req/s ×
  2KB = 400KB/s — a Raspberry Pi could serve this`. Small numbers said
  out loud prevent big architecture.
- Uncertainty in load estimates propagates: say which conclusions survive
  if the estimate is 10× off, and which don't.
- No resume-driven design. If the honest answer is "a managed Postgres
  and a queue, done", that's the answer.

## Quality gates

- The Now/Next/Scale levels are all present (or a level is explicitly
  marked unnecessary with why).
- Every Next/Scale item carries a trigger metric.
- All load numbers are user-provided, measured, or labeled estimates with
  visible arithmetic.
- At least one item is explicitly marked **"don't do yet"** — a design
  review that only adds things hasn't finished its job.

## Stop conditions

- Levels delivered with triggers and open questions → done.
- The design question turns out to be a correctness bug → route to
  backend/root-cause work; scale redesign later.
- Load numbers can't be obtained or estimated → deliver the decision
  framework with the estimate ranges that would flip each choice, and
  say what measurement to take first.

## Output contract

In chat: the first question answered with the user's numbers, then
Now/Next/Scale (each ≤ 6 lines), open questions.

On disk (when the design will guide later work): `docs/design/<slug>.md`
with provenance header (`<!-- generated by headroom on YYYY-MM-DD -->`),
the numbers used, dimension analysis, the three levels, and the "don't do
yet" list. This is the artifact `blueprint` documents and `masterplan`
slices against when the design gets implemented.

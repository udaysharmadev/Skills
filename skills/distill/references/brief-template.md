# Brief template + worked example

## Implementation-readiness review

Run this review as an implementer with no conversation history. Every item
must pass before the brief ships:

1. The target actor, triggering condition, and desired outcome are clear.
2. Scope and non-goals prevent the most tempting adjacent work.
3. Existing paths/commands are observed or visibly provisional.
4. Every material behavior has a success and relevant failure/edge condition.
5. Permissions, data effects, compatibility, and irreversible actions are
   explicitly bounded where applicable.
6. Acceptance criteria can be proven at the right boundary, not merely
   acknowledged by a human.
7. Assumptions have identifiers, are falsifiable, and carry an owner/review
   trigger when they are material.

## Template

```markdown
<!-- generated by distill on YYYY-MM-DD -->
# Brief: <title>

## Goal
<One sentence: what becomes true, for whom.>

## User outcome
<What the user experiences differently. One or two sentences.>

## Context
- <Existing piece the work touches: path + one line.>
- <Command/environment facts that constrain the work.>

## Constraints & conventions
- <Project conventions discovered in the repo that must be respected.>

## Scope
- <In: concrete deliverables.>

## Non-goals
- <Out: explicitly not doing, tempting as it is.>

## Agent-executable specifications
- [ ] <Unambiguous, checkable statement a downstream agent can verify without human judgment.>
- [ ] <Example: "Toggling the theme writes 'dark' or 'light' to localStorage", not "Theme looks good.">

## Edge cases
- <Empty/error/loading/malformed states worth handling.>

## Non-functional requirements
<Only when they bite: performance budget, accessibility bar, i18n,
security constraint. Omit the section if nothing exceeds the project's
existing bar.>

## Compatibility & migration
<Only when existing data/users are affected: what stays backward
compatible, what migrates, what breaks.>

## UX expectations
<Only for user-facing work: behavior expectations, not visual design.>

## Verification
- <Command that must pass, e.g. `npm test`.>
- <Human/browser check, e.g. "user can toggle theme and it survives reload.">

## Known unknowns & assumptions
- A1: <falsifiable assumption made instead of asking.>
- U1: <open question, non-blocking.>

## Suggestions (non-binding)
- <At most 3, clearly optional.>
```

## Worked example (abridged)

Input: "bro add dark mode make it good"

```markdown
# Brief: dark mode toggle for the dashboard

## Goal
Users can switch the dashboard between light and dark themes, and the
choice persists across sessions.

## User outcome
Comfortable viewing in low light; the app remembers the preference.

## Context
- Tailwind configured with CSS variables: `tailwind.config.ts`
- Theme not stored anywhere today; no user preferences table exists.

## Constraints & conventions
- Colors must come from existing CSS variables (no hardcoded hex).
- Follow existing toggle component pattern in `src/components/Toggle.tsx`.

## Scope
- Theme toggle in the settings page + header
- Persisted preference (localStorage; no account-level sync)
- Default follows `prefers-color-scheme`

## Non-goals
- Per-user server-side theme storage
- Theming beyond the two modes

## Agent-executable specifications
- [ ] Toggling switches theme with no full page reload
- [ ] Preference survives page reload and is readable from localStorage
- [ ] First visit matches OS preference (prefers-color-scheme)
- [ ] No flash of wrong theme on load (blocking script injection if SSR)

## Edge cases
- OS preference changes while app is open (only applied on next visit)
- `localStorage` unavailable (falls back to OS preference)

## Verification
- `npm run build` and `npm test` pass
- Manual: toggle → reload → verify persistence in both directions

## Known unknowns & assumptions
- A1: localStorage is acceptable persistence (no auth system exists).
- U1: should the auth page (future) also respect the theme?

## Suggestions (non-binding)
- Consider `next-themes` if hydration flash proves annoying.
```

Note what the example *doesn't* contain: no Tailwind tutorial, no design
philosophy, no invented requirements. That's the target density.

## Risk-bearing feature minimum

For a nontrivial feature, preserve explicit non-goals and numbered assumptions
even in a short brief. An auth/tenant change must describe which actor owns each
resource, where access is enforced, what is denied across users, and what old
unauthenticated behavior changes. Do not choose a provider or password model
when that is an unresolved product/security decision.

Use acceptance pairs: condition → required result → observation. For example,
"user B requests user A's order → no order data returned → API negative case".
A build passing proves buildability, not this authorization contract. For
multiplayer/offline/time-zone requests, include only relevant ownership,
reconnect/conflict, and clock boundaries. Proposed new surfaces are labeled
`new`; missing surfaces the request assumes already exist stay unresolved.
